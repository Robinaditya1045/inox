## Project overview

Inox is a synchronized watch-party platform: three independently deployable apps in one monorepo — a Go backend (REST API + WebSocket hub + WebRTC SFU), a React/Vite viewer client (`frontend/`), and a React/Vite admin dashboard (`admin-portal/`).

## Commands

### Local infrastructure
- `make up` / `make down` — start/stop Postgres, Redis, MinIO, pgAdmin via Docker Compose
- `make dev` — starts infra, then runs backend + frontend + admin-portal concurrently (ports 8080 / 5173 / 3000)
- `./dev.sh` — same three services in a tmux session (`inox`) instead of `concurrently`
- `mprocs` — same three services driven by `mprocs.yaml` (requires the `mprocs` binary)

### Backend (`backend/`, Go 1.25)
- `go run ./cmd/server` — run the API/WebSocket server
- `go run ./cmd/worker` — run the asynq background worker (media transcoding)
- `go run ./cmd/migrate --command=up|down|status [--steps=N] [--dir=migrations]` — hand-rolled SQL migration runner (not golang-migrate); run with `backend/` as cwd, or pass `--db`
- `go build ./...`, `go vet ./...`
- `go test ./...` — full suite; CI runs `go test -v -race ./...`
- Single test: `go test ./internal/auth/... -run TestName -v`
- Tests use stdlib `testing` with hand-written in-memory fakes (no testify/mockgen)

### Frontend (`frontend/`) and Admin Portal (`admin-portal/`)
Both are separate Vite + React 19 + TypeScript apps with identical scripts. They style themselves differently and are not interchangeable: `frontend/` uses CSS Modules + CSS custom properties (`src/styles/theme.css`), while `admin-portal/` uses Tailwind v4 via `@tailwindcss/vite` (`@import "tailwindcss"` in `src/index.css`, with only genuinely custom rules — theme vars, motion tokens in `@theme` (`ease-snappy`, `animate-enter`, dialog/overlay animations), scrollbar, badge glows, the reduced-motion override — kept alongside it). Don't hand-write utility classes into `admin-portal/src/index.css`; let Tailwind generate them.

In `frontend/`, every colour, space, radius, shadow and motion value is a token in `theme.css` — reference those rather than raw values. Entrance animations are exposed as `--animate-*` variables (keyframes live in `src/index.css`) because CSS Modules would otherwise rename a global keyframe referenced by name; use `animation: var(--animate-rise-in)` etc., and `utils/motion.ts` `stagger(i)` for list stagger. Reuse the primitives in `components/common/` (`Button`, `IconButton` (with built-in tooltip), `Modal` (Radix Dialog), `Tooltip`, `TextField`, `Tabs`, `Skeleton`, `EmptyState`, `Alert`, `Badge`, `Avatar`) and `useToast()` for transient confirmations (it returns an id for `dismiss`, and takes `actions` for Accept/Reject-style buttons) instead of hand-rolling them; `IconButton`/`Tooltip` need the `TooltipProvider` mounted in `App.tsx`.

`admin-portal/` is laid out like YouTube Studio: a sidebar shell (`components/layout/AppLayout.tsx`, `Sidebar.tsx`) around routed pages in `src/pages/` — `/dashboard`, `/content` (the library table; filters live in the query string), `/content/:assetId/details|captions`, `/live`, `/rooms` (all rooms, public and private, with bulk delete via `useAdminRooms`; `?view=live` is the telemetry-driven inspector), `/community` (writing platform-update posts), `/tracing`. Routing is a data router (`createBrowserRouter` in `App.tsx`, basename from Vite's `BASE_URL` because the portal is also served under `/admin/`), which `useBlocker` needs for the unsaved-changes guard on the details page. Content-management pieces live in `components/content/`; its primitives in `components/ui/` (`Menu` — portalled so the table's scroller can't clip it, `IconButton`, `ConfirmDialog`, `ToastProvider` + `hooks/useToast`). New code uses `cx()` to join classes: the older `cn()` buckets classes by prefix and silently drops one of e.g. `text-center text-[13px]`. hls.js is an npm dependency loaded with a dynamic `import()` by `components/content/VideoPlayer.tsx` (not the CDN, and not in the initial bundle).
- `npm run dev` — Vite dev server
- `npm run build` — `tsc -b && vite build`
- `npm run lint` — ESLint
- `npx tsc --noEmit -p tsconfig.app.json` — typecheck only (what CI runs)
- Neither app has a test runner configured yet (no vitest/jest) — don't assume `npm test` works.

Root `package.json` only wires up Husky + lint-staged: `gofmt`/`goimports` on `backend/**/*.go`, `prettier` on `frontend/`/`admin-portal/` `.ts(x)/.js(x)/.css/.md`, run automatically on commit.

## Architecture

### Three deployables, one repo
- `backend/` — Go service exposing a REST API, a WebSocket hub for room events, and a Pion-based WebRTC SFU for voice chat/screen share. Entry points: `cmd/server` (API), `cmd/worker` (asynq media processing), `cmd/migrate` (schema).
- `frontend/` — the watch-party client end users join: synced video playback, chat, and voice/screen-share.
- `admin-portal/` — a separate operator dashboard (room inspector, media catalog, live telemetry), deployed independently (Vercel) from a different origin than the backend — this is why CORS and session-cookie `SameSite` handling matter.

### Backend layering (`backend/internal/`)
`app.App.Run()` is the single composition root: it wires repositories, services, the WS hub, and the SFU manager, then owns graceful shutdown. `api/router.go` registers all routes on the stdlib `net/http.ServeMux` (Go 1.22+ method+pattern routing) and layers `CORS → RequestLogger → metrics` around it; handlers live in `api/handler`, cross-cutting concerns (`RequireAuth`, `RequireRoomMembership`, `RequireAdminRole`, `RateLimit`) in `api/middleware`. Domain packages (`auth`, `room`, `media`, `sfu`, `ws`, `observability`) each expose a repository + service pair; `domain/` holds shared structs. `storage` abstracts MinIO vs. local-filesystem media storage and falls back to local automatically if MinIO is unreachable at boot (see `app.Run`).

### Auth & sessions
Session-based, not JWT: `auth.SessionStore` persists sessions in Redis under cookie name `inox_session`. `RequireAuth` also accepts `Authorization: Bearer`, `X-Session-ID`, or `?session_id=` as fallbacks (useful where a client can't set custom headers). Cookie `SameSite` is `Lax` in development and `None`+`Secure` in production/staging, because `admin-portal`/`frontend` and the backend live on different origins in deployment. `config.Load()` refuses to start in prod/staging if `SESSION_SECRET` is the default value or under 32 characters.

There is no `role` column on `users`: `domain.Session.Role` is always `user`, so admin access (`RequireAdminRole`, gating `/api/v1/admin/*` and `/metrics`) is granted solely by listing an address in the `ADMIN_EMAILS` env var. Without it every admin route returns 403.

Avatars (`auth.AvatarService`, `/api/v1/users/profile/avatar`: `POST` multipart upload, `PUT` an image link, `DELETE` to clear) are either uploaded under `avatars/` with a fresh key per upload or linked elsewhere. Unlike media URLs, an uploaded avatar's URL is stored already pointing at the public stream proxy (`MEDIA_STREAM_BASE_URL`), because session, `/users/me`, friends, chat and member lists all hand `avatar_url` straight to browsers without `publicURL` rewriting. Replacing or clearing an uploaded avatar, by any of the three routes, deletes its file. The viewer center-crops uploads to a ≤256px square JPEG before sending them (`utils/cropAvatar.ts`).

Neither client app talks to the API with bare `fetch`. Each has one client that attaches the base URL and credentials — `frontend/src/api/client.ts` and `admin-portal/src/lib/api.ts` — sending `credentials: 'include'` plus `Authorization: Bearer` / `X-Session-ID` from the `inox_session_id` localStorage key. Route new calls through those; a relative `fetch('/api/v1/...')` only works behind the Vite dev proxy and 404s once deployed. The admin portal has no login screen of its own, and localStorage is origin-scoped, so it adopts a session from `?session_id=…` on first load (`bootstrapSessionFromUrl`, called in `main.tsx`) and strips it from the URL. WebSocket handshakes can't carry headers, so the telemetry socket passes the session as a query parameter instead.

### Real-time protocol
Chat, playback sync (`PLAY`/`PAUSE`/`SEEK`/`CHANGE_MEDIA`/`SYNC_PLAYBACK`), and WebRTC signaling (`SFU_OFFER`/`SFU_ANSWER`/`SFU_ICE_CANDIDATE`) all flow over one WebSocket per room as typed `ws.Event` JSON messages (`backend/internal/ws/event.go`). `ws.Hub` fans events out per room; when Redis is configured, `RedisEventBus` mirrors events across processes so the hub scales horizontally. Voice/camera/screen-share RTP media itself doesn't cross the WebSocket — only SDP/ICE signaling does; actual audio/video is routed through `sfu.Manager` (one Pion-backed `sfu.Room` per room acting as a selective forwarding unit). The SFU renames every forwarded track `<kind>.<userId>` (`mic`/`camera`/`screen`), which is how clients attribute remote media. A camera and a screen share are both just video on the wire, so the browser declares what each of its MediaStreams is in a `streams` map (keyed by stream ID) on every `SFU_OFFER`/`SFU_ANSWER` it sends; undeclared video is treated as a screen share.

A room can also play through a playlist. Members send `QUEUE_SET` / `QUEUE_ADVANCE` / `QUEUE_CLEAR`; the hub owns the queue (`RoomPlaybackState.Queue`, also sent on `SYNC_PLAYBACK`) and answers with a playing `CHANGE_MEDIA` plus `QUEUE_STATE`, and never relays the commands themselves (`ws/queue.go`). Every controller whose video ends sends `QUEUE_ADVANCE` with `from_index`, and the hub drops any that no longer match, so the room moves on once. A plain `CHANGE_MEDIA` to a URL in the queue moves the queue there; any other URL clears it. Queues are treated as immutable (replaced, never edited in place) because playback state is snapshotted for Redis from other goroutines. Playlists themselves (`internal/playlist`, `/api/v1/playlists`) are private to their owner and copied into the queue when started.

Whoever opens an empty room chooses what it watches. The hub sets `first_in` on the `SYNC_PLAYBACK` it sends that connection, and the viewer (`PlayerSyncProvider` `arrival`, once per visit; `RoomPage`) opens the library for anyone who can control playback, with a `ContinueWatching` card for what the room was left on above the grid. When the last viewer leaves, `parkPlaybackState` pins a playing VOD to where it got to and stamps `EmptiedAt`; on the next arrival it comes back paused there, unless that was within `emptyRoomGrace` (30s, a lone viewer's reconnect), in which case it is still playing and no library is shown. A room deleted outright is not parked.

Deleting a room (owner `DELETE /rooms/{id}`, or admin `DELETE /admin/rooms/{id}` / `POST /admin/rooms/delete` with `{"room_ids": [...]}`, which work on any room whoever owns it) calls `Hub.CloseRoom`: everyone still connected gets `ROOM_CLOSED` and their socket is closed, and the viewer returns to the lobby. The service also clears the room's Redis playback state and cached membership checks, since those would otherwise keep relaying events from the dead room.

Kicking (`DELETE /rooms/{id}/members/{user_id}`) and leaving call `Hub.RemoveMember`, which sends that user `REMOVED_FROM_ROOM` and closes all their connections to the room, since a socket outlives the membership it was opened with; the viewer returns to the lobby with a toast. It is not a ban — anyone can rejoin a public room, and opening its page does so.

Online/offline status in the member list comes from `PRESENCE` (`ws/presence.go`): the full list of distinct users connected to the room, sent to the whole room on every connect, disconnect and eviction, and replaced wholesale on the client. Don't derive it from `JOIN_ROOM`/`LEAVE_ROOM` — those fire per connection (closing one of two tabs isn't leaving) and evictions send none. `RoomProvider` holds the list (`onlineUsers`) because it's only sent on change, and re-reads the member roster when someone unknown appears or someone drops off; the roster itself is always the room's membership, so offline members stay listed. Like `RoomActivity`, it's per process and is delivered locally, not over the Redis bus.

Inviting someone to voice is a pair of targeted events: `VOICE_INVITE` to the invitee and `VOICE_INVITE_REPLY` (`{accepted}`) back to the inviter, both relayed only to their `target_id`. The hub (`ws/voice_invite.go`) drops invites that are untargeted, sent to yourself, sent by someone with no SFU peer (you invite people to join you), or repeated to the same person within 15s. `RTCProvider` owns both ends: the invitee gets a toast with Accept/Reject (Accept calls `connectAudio` from the click, which the mic prompt and autoplay need; letting it expire sends no reply), and the member list shows an invite button beside online members who can stream audio, while you're connected.

`ws.Hub` state (`rooms`, `playbackStates`) may only be touched on its `Run` loop — it has no locks. Other goroutines ask the loop instead: `Hub.RoomActivity(ctx)` sends a request over `activityRequests` and gets a snapshot back. `GET /api/v1/rooms` uses it to attach `activity` (distinct connected viewers, `is_playing`, media URL/kind) to each listed room, which the lobby polls every 15s (`useRoomListPolling`) to build its "Now Streaming" section. Titles and artwork are matched client-side against `GET /api/v1/media` by URL (`utils/roomActivity.ts`). Counts are per process: with the Redis event bus, a room spread over several processes reports only the local share. `InspectRooms` (for the telemetry hub) asks the loop the same way, and the Redis subscription hands received events to the loop through `deliverRemote` rather than calling `dispatchLocal` itself; `ws/loop_internal_test.go` only catches a regression in either under `-race`.

On the frontend this maps to matching Context+Provider+hook triples — `AuthProvider`/`auth.context`/`useAuth`, `RoomProvider`/`room.context`/`useRoom`, `RTCProvider`/`rtc.context`/`useRTC` — all built on top of one `useRoomSocket` connection. `rtcService` (`frontend/src/services/rtc/rtc.service.ts`) wraps the raw `RTCPeerConnection`; `RTCProvider` owns signaling and exposes connection/mute/deafen/screen-share state.

Browser autoplay policy is relevant here: `AudioRenderer` creates `<audio>` elements for remote SFU tracks asynchronously (often well after the click that started signaling), so it explicitly calls `.play()` and retries on the next `pointerdown`/`keydown` if the browser blocks it — don't revert to relying on the bare `autoplay` attribute, since that fails silently whenever a peer's track arrives without a very recent, directly-linked user gesture.

### Media pipeline
Uploads go through `media.Service` → `storage.Service` (MinIO or local disk) → an asynq job picked up by `cmd/worker`, which transcodes to HLS. The uploader picks which rungs of the 1080p/720p/480p ladder (`media/profiles.go`) to encode — each is a separate x264 encode, so fewer finish sooner — via `transcode_profiles` on the multipart upload or the presigned-URL request. The choice is stored on the asset (migration 017; empty means the full ladder), not just in the task, because worker retries and `ReconcileOrphanedAssets` only have the asset to go on. `mediaHandler.StreamProxy` serves both raw assets and HLS segments; `ReconcileOrphanedAssets` runs at boot to recover jobs stuck from a previous server crash. The transcoder also records `duration_seconds` and, unless a poster was uploaded (`POST /api/v1/admin/media/{id}/thumbnail`), captures one from the video under `thumbs/`; `BackfillThumbnails` queues a `thumbnail:media` task at boot for ready VOD assets still without one. Anything left without a poster (live channels, unreachable external links) gets the single shared default drawn by the viewer's `MediaPoster`. `PATCH /api/v1/admin/media/{id}` edits title/description or points the poster at an image link (stored as-is, never fetched — no SSRF surface); `DELETE /api/v1/admin/media/{id}/thumbnail` drops a custom poster and queues a fresh capture. The portal crops every uploaded or frame-captured poster to a 16:9 JPEG client-side before upload.

Captions (`media_captions`, migration 016) are one WebVTT track per language per VOD asset, stored under `captions/` with a fresh key on every save (so the stream proxy caches them like posters) and purged on replace/delete. `media.NormalizeCaptions` validates WebVTT and converts SubRip; the backend is the authority on what a valid track is. Tracks ride along on `GET /media` and `GET /media/{id}`, and viewers look them up with `GET /api/v1/media/captions?url=<what the room plays>` — rooms only know media by URL, the lookup also matches by storage key because `NormalizeAsset` rewrites hosts, and a `/media/{id}/captions` route would overlap the `/media/stream/` prefix (the mux panics on that). The viewer draws captions itself (`CaptionOverlay`) rather than with a native `<track>`, which would need the `<video>` in CORS mode (breaking linked files on hosts without CORS) and would render under the custom controls; whether captions are on is per viewer (localStorage), not room-wide.

### Community (platform updates)
Admins post platform updates — new features, improvements, fixes, announcements — that every viewer reads on the viewer's `/community` page (`internal/community`, `community_posts`, migration 018). Viewers read `GET /api/v1/community/posts` (`?category=&limit=&offset=`, pinned first, then newest); admins manage posts under `/api/v1/admin/community/posts` from the portal's `/community` page. A post with a null `published_at` is a draft that only admins see; editing a published post keeps its date, and unpublishing clears it. Bodies are plain text, never HTML: blank lines split paragraphs, `- ` lines are bullets, and bare http(s) links are made clickable. Both apps parse them with the same rules (`utils/postBody.ts` / `lib/postBody.ts`), so change both together. The viewer's nav badge counts posts newer than the newest `published_at` this browser has seen (localStorage `inox_community_last_seen`; a server timestamp, so clock skew can't hide posts).

### Observability
`observability.EventAggregator` batches and persists WS/room events to Postgres for historical analytics. `observability.TelemetryHub` streams a live snapshot over `/api/v1/admin/telemetry/ws` to the admin portal's `SystemPulseDashboard`/`LiveTelemetryChart` — one snapshot on connect, then every 2s. `/metrics` exposes Prometheus format, gated by `RequireMetricsAccess`.

`useTelemetryStream` is owned by `admin-portal/src/App.tsx`, not by the dashboard, and handed down through `lib/contexts.ts` (as is `useMediaCatalog`): routes mount and unmount, so hooking it lower down tore down the socket and discarded chart history on every navigation. It also feeds the header's connection badge and the Room Inspector's live rooms. Its liveness watchdog compares two local `Date.now()` readings — never the server-sent `timestamp` — since server/browser clock skew above the 10s threshold would otherwise close a healthy socket every 5s.

Each panel falls back to built-in mock fixtures when the backend is unreachable ("demo mode"). Keep that state honest: demo mode must not report `isConnected`, and mock samples must not be mixed into live chart history or used to decide whether the backend is alive.
